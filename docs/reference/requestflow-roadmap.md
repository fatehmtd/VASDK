# RequestFlow Implementation Roadmap

Reference target: the ticket-sized milestone breakdown for actually building `va::orchestrator` - who builds what, in what order, and what "done" looks like for each piece. This is the implementer-facing companion to [requestflow-spec.md §15](requestflow-spec.md#15-rollout-plan): §15 stays the authoritative phase *summary* (and the source of truth if this document ever drifts from it); this document exists because §15's Phase 4 in particular bundles roughly fifteen independently-shippable features into one paragraph, which isn't small enough to plan or staff against.

Status: **Draft v1.** Written before any `va::orchestrator` code exists - see the note in [§0](#0-current-state).

## 0. Current State

M0 (module scaffolding), M1.1 (proto schema/codegen), M1.2 (`OrchestratorConfigLoader` + `validate()`), M1.3 (`PhraseGrammarMatcher`, the §22.1 phrase-grammar compiler), M1.4 (`ExpressionEvaluator`, the §8 expression evaluator), M1.5 (`ParameterValidator`, the §7 parameter model), M1.6 (`OrchestratorEngine`/`OrchestratorFrameProcessor`, event/condition routes only, plus the live `SessionState`), M1.7 (`SessionPersistence`/`FileSessionPersistence` plus `OrchestratorEngine`'s restoring constructor, per §10), and M1.8 (`OrchestratorConversationSimulator` plus the four §11 metrics M1.6/M1.7's engine can actually produce - the rest wait on Phase 2/3/4's NLU/webhook/handoff producers) are done and committed - this closes out Phase 1. M2.1 (`NLUProvider` interface plus `TrainingPhraseNLUProvider`, wrapping M1.3's phrase-grammar compiler behind it, per §5/§22) is also done and committed - `NLUContext`/`RankedIntent`/`NLUResult` (§5) were added to `domain.proto` alongside it. M2.2 (`LLMNLUProvider`, a structured classification call against `LLMTransport`, per §5/§22.2) is done and committed too - a single request/response round trip, parsed as JSON (`nlohmann::json`, matching every other LLM-facing file in this codebase) rather than through `google::protobuf::util::JsonStringToMessage`, which turned out to be fragile once more than one statically-linked copy of libprotobuf exists in the same process (the self-test executable's own copy plus `libVASDK`'s). Checking `interrupt_intent_names` (§6.2) and populating `co_intents` (§6.1) are deliberately not implemented by either provider yet - both are Phase 4 items per §5 below. M2.3 (`intent` routes wired into §6 step 2/3, using either provider) is done and committed too: `OrchestratorEngine::setNLUProvider()` attaches an `NLUProvider` (unset is still a fully supported, provider-optional shape); `handleUtterance()` calls `detect()` once per turn, but only when the active node actually has at least one `intent`-triggered route, to avoid a wasted call (a real network/LLM round trip for `LLMNLUProvider`) when nothing on the node could consult the result. The resulting `NLUResult` is cached for the rest of that turn - including any `node_enter`/`emitEvent` cascade - so `intent` routes can match it in step 3 (right after `event` routes, before `condition` routes, same priority-ordering rule as the other two groups) and its `extracted_parameters` populate the `nlu.*` namespace `ExpressionEvaluator` reserved back in M1.4. `expected_parameter_name` is never set (that needs M2.5's `expect`/form machinery), and `context.interrupt_intent_names`/`NLUResult.co_intents` stay unconsulted (Phase 4, same deferral as M2.1/M2.2). `OrchestratorConversationSimulator` gained `setInjectedNLUResult(utterance, result)` (spec §12/§20.2's own shape - keyed by exact turn text, bypassing any real provider for that turn) and a `setNLUProvider()` passthrough, so intent-route tests can be either fully deterministic or exercise a real provider end to end. M2.4 (`llmGenerate` executor action per §9.3, generative nodes per §9.4) is done and committed too: `OrchestratorEngine::setLLMTransport()` attaches the `va::llm::LLMTransport` both features call, and `setCustomToolHandler()` registers the same deterministic-C++ handler map (§9.6) whether the call comes from an ordinary route's `CustomToolAction` (now wired into `runAction` - `args_cel` evaluated into a `Struct`, return value discarded) or a generative node's LLM-tool loop. `handleUtterance()` checks `Node.generative` first and, when true, skips `NLUProvider.detect()` and §6 steps 1-3 entirely in favor of `runGenerativeTurn()`: a system message (`generative_config.system_prompt_template`, `{param}`-substituted like `say.text`, plus a tool-calling contract this engine defines itself - reply with only `{"tool": "<name>", "args": {...}}` to call a tool, anything else is spoken text) is installed once per node-entry, then each external turn's utterance drives one exchange of tool-call/tool-result round trips (via the same `LLMTransport::injectToolResult()` a real function-calling loop would use) until the model replies in plain text or calls a `terminal` tool - either way emitting `generative_config.exit_event` (default `generative_exit`) as a pending event, re-entering ordinary route evaluation at step 3 exactly like any other emitted event. A tool name outside `generative_config.tools` is refused even if a handler happens to be registered under that name elsewhere (enforcing the "LLM cannot call anything outside that list" rule server-side, not just via prompt text); `_generativeTurnsUsed` (reset on every node entry) enforces `max_turns` by force-exiting the *next* turn without forwarding it to the LLM at all; a separate, spec-silent `kMaxToolCallsPerTurn` constant bounds back-to-back tool calls within one turn's exchange so a misbehaving model can't hang the synchronous call forever. `LlmGenerateAction` (an ordinary route action, distinct from a generative node) is a simpler one-shot, stateless call - history cleared first, `prompt_template` rendered with the same `{param}` substitution, and the model's raw reply spoken verbatim with no JSON contract, since its whole job is producing free text. Deliberately deferred, matching M2.2's own scope decision for its classification round trip: every external call here (`llmGenerate`, the generative loop's exchanges, `customTool`) runs synchronously in `BLOCKING` mode only - no thread pool, no `turnExternalCallBudget`, no `ControlFrame::INTERRUPT` barge-in cancellation (§9.1/§9.3) - since this engine still has no threading infrastructure at all; that lands together with M3.1's `callWebhook` reliability model, the natural place to build it once for every off-thread action kind rather than duplicating a one-off version here. A `customTool` action naming an unregistered handler, or a generative node/`llmGenerate` action reached with no `LLMTransport` attached, throws `std::runtime_error` - the same "fail loudly" treatment `enterNode` already gives an unknown flow/node id, since both are the same class of bug (config assumes wiring the app never completed). M2.5 (`expect` executor actions, typed and bare, per §9.5 - depending on M2.1-M2.3's extraction path) is done and committed too: it turned out to need building the static-form parameter collection machinery (§7) alongside `expect` itself, since spec §9.5 is explicit that a `pending_ask`'s extraction/validation/reprompt "run through the exact same code path a static-form parameter already uses" - and that code path never existed until now (M1.6's own class comment already flagged `expected_parameter_name` as never set, "needs the expect/form machinery M2.5 hasn't shipped yet"). `handleUtterance()`'s step-2 priority chain is now real: a `PendingAsk` (`_session.hasPendingAsk()`, armed by a prior turn's `ExpectAction`) wins first if its `parameter` is present; otherwise the active node's `form`, first required-and-unfilled `Parameter` in declaration order (`findUnfilledFormParameter()`, reusing `ParameterValidator::isRequired()` for the `condition_cel` check - both shipped in M1.5 but never called by the engine until now); otherwise the ordinary M2.3 candidate-intent path. A bare `PendingAsk` (no `parameter`) is cleared and falls straight back through that same chain - spec §9.5's own "exactly as if the node had just started a fresh turn." `handleParameterExtractionTurn()` runs `NLUProvider.detect()` (or `injectedResult`, same simulator convention M2.3 established) with `expected_parameter_name` set, validates whatever lands in `NLUResult.extracted_parameters` via a new `ParameterValidator _parameterValidator` member (`registerParameterValidator()` exposes `validator_ref` registration), and either stores it (tagged `source: "expect"` or `"nlu"` in `SessionState`'s new `ParameterMeta` bookkeeping) and falls through to step 3 the same turn, or - "this step does not consult routes" - picks `prompts.reprompts[attempts-1]`/`prompts.escalation` and ends the turn right there with no route evaluation at all (a new `parameter_validation_failures` counter increments here, spec §11). `SessionState` gained `PendingAsk`/`ParameterMeta` tracking (a `hasPendingAsk()` bool distinct from the `PendingAsk` proto's own contents, since a bare ask's default-valued proto is otherwise indistinguishable from "no ask armed") and both round-trip through `OrchestratorEngine::snapshot()`/the restoring constructor now, since spec §9.5 explicitly requires a mid-ask session to survive restore. The `expect` action itself (`runAction`'s new `Action::kExpect` case) says `parameter.prompts.initial` (typed) or nothing (bare) exactly like `SayAction`, arms the `PendingAsk`, and sets a new `_suspendTurn` flag that ends the call's processing immediately end-to-end - `runExecutor()` stops running further actions (defense-in-depth; see the `OrchestratorConfigLoader::validate()` placement check below), `fireRoute()` skips that route's own `Transition` (treated like `_ended`), `enterNode()` skips queuing `node_enter` when `entry_executor` itself suspended the turn, and `runToQuiescence()`'s cascade loop stops - all mirroring how `_ended` already short-circuits the same call chain. A new `finishTurn()` helper (replacing every bare `runToQuiescence()` call site) additionally calls `checkFormParameterAsk()` once the cascade settles, unless the turn already ended or suspended: this is what says a static-form parameter's `prompts.initial` the moment a node freshly lands with a required, unfilled, never-before-asked parameter - spec §19's `collect_reason`/`collect_date` worked example, turn-by-turn. `OrchestratorConfigLoader::validate()` gained the §9.5 "placement constraint" check (`expect` must be the last action in its `Executor` - anything after it is unreachable, since `expect` ends the turn on the spot); the dead-end-node check and `Node.form`/`expect` recognition it already needed were both already built in M1.2, ahead of either feature actually existing. `LLMNLUProvider` gained a second, differently-shaped structured call (`detectParameterExtraction()`/`buildExtractionPrompt()`) for `context.expected_parameter_name()` - a classification prompt has no notion of "the value for this one named slot," so this completes the `NLUProvider` contract's slot-filling half for the LLM-backed provider the same way `TrainingPhraseNLUProvider` already implemented it back in M2.1. Deliberately deferred: the no-input half of §9.5 (`Parameter.no_input_timeout_ms`, `ControlFrame::SET_LISTEN_TIMEOUT`, `EventHandlers.no_input`) - there is still no `OrchestratorFrameProcessor`-side turn-detection integration to signal it from, so only the validation-failure reprompt/escalation cycle is implemented, fully exercisable through the simulator; and the `EventHandlers.no_match` fallback chain, a separate, not-yet-scheduled gap orthogonal to slot-filling that predates this milestone. M3.1 (`callWebhook` with the full [§9.2](requestflow-spec.md#92-callwebhook-execution-model) reliability model) is done and committed too - the first Phase 3 milestone, and the first to actually run an `EventHandlers` executor at all (`node_handlers`/`flow_handlers`/`global_handlers`, previously load-time-validated by M1.2's own ahead-of-the-feature "handler coverage" check but never executed). `runAction`'s new `Action::kCallWebhook` case (`handleWebhookAction()`) dispatches the blocking `HttpInterface::post()`/`get()` call - and its one permitted retry - as a single task on a new `WebhookThreadPool` (pimpl'd behind a forward-declared `unique_ptr` member so `OrchestratorEngine.h` stays free of `<future>`/`<thread>`; sized `OrchestratorConfig::executorThreadPoolSize`, previously an inert tuning field since M1.6), while the calling thread waits on the returned `std::future` bounded by `OrchestratorConfig::turnExternalCallBudget` - simplified to apply in full to each individual `callWebhook` action rather than a shared, decreasing budget across multiple calls in one turn, since spec doesn't describe subdividing it and multiple `callWebhook` actions in one `Executor` is an edge case, not the documented scenario. `isTransientFailure()` implements spec's "never on 4xx" rule directly against `CurlHttpProvider`'s own error shape: a `NetworkErrorCode::HttpError` with `httpStatusCode < 500` is permanent (no retry), everything else (5xx, timeout, connection/TLS/protocol failure) gets the one retry `OrchestratorConfig::webhookMaxRetries` allows. A small per-endpoint circuit breaker (`kCircuitBreakerFailureThreshold` consecutive failures opens it for `kCircuitBreakerCooldown` - both engine-chosen constants, since [§18](requestflow-spec.md#18-open-decisions) leaves the exact shape open beyond "one retry on transient errors") refuses a call outright once open, throwing `std::runtime_error` - spec's own "unrecoverable failures... surface as `ErrorFrame` upstream," the same "fail loudly" treatment this class already gives a missing `LLMTransport`/`customTool` handler, since `OrchestratorFrameProcessor` still has no `ErrorFrame`-wrapping of its own to route it through (a pre-existing gap, not new here). On failure, `handleWebhookFailure()` resolves `EventHandlers.webhook_error` via a new `findWebhookErrorHandler()` (node → flow → agent, first one present) and runs it with `event.status_code`/`error_message`/`url` populated - spec's "re-enter route evaluation at step 3... so `EventHandlers.webhook_error`... decides what happens next": since `domain.proto` itself documents `EventHandlers` as a distinct fallback mechanism rather than something an ordinary `Route.trigger.event` could ever match, running its `Executor` synchronously *is* that re-entry, standing in for "the matched executor" step 3 would otherwise run (it has no `Transition` of its own - an author reaches one only indirectly, via an `emitEvent` a real node `Route` can catch, drained by the same `runToQuiescence()` this whole call already returns into). A new `_abortExecutor` flag (reset every external call like `_suspendTurn`, but always consumed-and-reset the instant `runExecutor()`/`fireRoute()`/`enterNode()` sees it, since unlike `_suspendTurn` it never needs to propagate further) stops the *failing* route's own remaining actions and skips its own `Transition` without ending or suspending the turn - the fallback chain decided what happens next instead, and the session stays live. On success, `applyWebhookResponse()` parses the JSON body per [requestflow-backend-spec.md §3](requestflow-backend-spec.md#3-the-webhook-response) and applies `messages`/`parameterPatches`/`transition`/`emitEvents`/`endSession` in that order, reusing existing machinery throughout (`parameterPatches` tagged `source: "webhook_patch"` - already named in `ParameterMeta`'s own proto comment; `endSession` builds a synthetic `Transition{END_SESSION}` through the existing `applyTransition()` rather than duplicating its completion-metrics logic); `handoff` is parsed and deliberately ignored - "fires `setOnHandoff` the same as a `HandoffAction`" needs wiring neither has yet (M3.3, "handoff/escalation end-to-end"). `routeId` now threads through `runExecutor()`/`runAction()` (previously just `eventParams`) - the one new per-call context `callWebhook`'s request body needs ([requestflow-backend-spec.md §2](requestflow-backend-spec.md#2-the-webhook-request)) that nothing before this milestone required; empty for `entry_executor` calls and the fallback handler's own executor, neither of which has a "matched route." `setHttpInterface()` attaches the transport (unset + a reached `callWebhook` throws, same "wiring never completed" treatment as a missing `LLMTransport`) - deliberately not passed through `OrchestratorConversationSimulator`, matching M2.4's own precedent of not extending the simulator for every new engine setter; self-tests attach a fake `HttpInterface` straight to a raw `OrchestratorEngine` instead. Two real bugs surfaced and were fixed while verifying this against a temporary self-test (34 assertions, since deleted): `compileAllExpressions()` had never walked any `EventHandlers` executor (only node `entry_executor`/route `executor`), so a `setParameter` inside a `webhook_error` handler reading `event.status_code` threw "expression was not precompiled" the first time one actually ran - now walks all six `EventHandlers` fields (agent-level once, then per-flow, then per-node), closing the same latent gap for `no_match`/`no_input`/`user_cancel`/`permission_denied`/`webhook_deferred` ahead of their own implementation; and `WebhookThreadPool`'s class definition was accidentally nested inside the file's anonymous namespace, making it a different type from the one `OrchestratorEngine.h` forward-declares for its pimpl'd member - caught at edit time, not by the compiler (both are named `WebhookThreadPool`; only one `unique_ptr` template instantiation would have been affected as long as nothing else collided). Metrics gained `webhook_latency_ms` (Sampler, one observation per `callWebhook` action - the whole wait including any retry, not per HTTP attempt) and `webhook_error_count` (Counter, once per action that ends in the `webhook_error` fallback; not incremented for a circuit-breaker refusal, which throws before there's an outcome to count) - both previously listed in [§11](requestflow-spec.md#11-observability) but unregistered since nothing produced them. Deliberately deferred, all explicitly Phase 3/4 items beyond this milestone's own scope: `handoff` end-to-end (M3.3); `ExecutionMode.FIRE_AND_FORGET`/`BEST_EFFORT` ([§9.10](requestflow-spec.md#910-action-execution-modes)) - `CallWebhookAction.execution_mode` is parsed but only `BLOCKING` is honored, matching M2.4's own `customTool`/`llmGenerate` scope decision; `PendingActionStore`/offline store-and-forward ([§9.9](requestflow-spec.md#99-offline-resilient-callwebhook-store-and-forward)); the permission gate ([§9.8](requestflow-spec.md#98-permission-gate)); and HMAC request signing ([requestflow-backend-spec.md §6](requestflow-backend-spec.md#6-authentication)), explicitly M3.2's own scope ("verify the engine's M3.1 output... including the HMAC signing") rather than this one's. M3.2 itself was skipped for now (it needs a live reference backend stub, deliberately deferred) in favor of M3.3 (`handoff`/escalation event handlers end-to-end), which is done and committed: two things, both synchronous, needing no new threading infrastructure. First, `handoff` end-to-end - a new `HandoffContext` message (`domain.proto`, spec §13/§20.1's own pseudocode only ever shows `ctx.sessionId`/`ctx.reason`, but a callback with nothing but those two is of little use to an app actually routing to a human agent, so it also carries `active_flow_id`/`active_node_id`/a `parameters` snapshot - a judgment call the spec leaves open, same class as M3.1's circuit-breaker constants) and a new `OrchestratorEngine::setOnHandoff(std::function<void(const HandoffContext&)>)`. `runAction`'s new `Action::kHandoff` case and `applyWebhookResponse()`'s new `handoff` field (backend-spec §3's `{reason}` object - previously parsed and silently ignored, per M3.1's own note) both now call one shared `fireHandoff(reason)`: increments the new `handoff_count` metric (unconditionally, same "the metric counts what happened, not whether the app was listening" precedent `webhook_error_count` already set), builds a `HandoffContext` from current session state, and invokes `_onHandoff` if attached. Second, `EventHandlers.no_match` - spec §6 step 3's "the node's no-match fallback (falling back to the flow's, then the agent's)," the "not-yet-scheduled gap" M2.5's own class comment flagged. `evaluateRoutesOnce()` now tracks whether any route actually fired across its event/intent/condition groups; when none did *and* this is the ordinary step-3 entry point (`eventName == nullptr` - immediately following step 2, not an internally-cascaded `node_enter`/`emitEvent` pass, which stays the silent no-op this engine already documented it as), a new `handleNoMatch()` runs whatever Executor a new `findNoMatchHandler()` resolves via the same node → flow → agent chain shape `findWebhookErrorHandler()` already established (kept as a separate near-duplicate rather than a shared member-pointer-templated helper - only two of these exist), with `event.attempts` populated from a new `_noMatchAttempts` counter (spec §8.2's table: "the reprompt count at the moment the fallback fired" - reset on `enterNode()` like `_generativeTurnsUsed`, otherwise a historical count not reset by an intervening successful match, matching `ParameterMeta.attempts`' own "historical failed-attempt count, not reset by success" precedent). No `_abortExecutor` involved here, unlike `handleWebhookFailure` - nothing is mid-executor at the point no_match fires, since it's only detected after every route on the node has already been tried and none matched. A new `no_match_count` metric increments alongside. Deliberately NOT implemented, both explicitly separate items: the no-input half of `EventHandlers` (`no_input`, spec §9.5) - still blocked on the same missing `OrchestratorFrameProcessor`-side turn-detection integration M2.5 flagged, no closer to existing now; and `user_cancel`/`permission_denied`/`webhook_deferred`'s own trigger paths (interrupt intents, the permission gate, `PendingActionStore` respectively) - all three remain Phase 4 roadmap items whose prerequisite machinery this milestone doesn't add, so there's nothing yet that could ever resolve their `EventHandlers` chain even if one were wired up. Verified via a temporary self-test (20 assertions, since deleted) covering `HandoffAction`/webhook-response-`handoff` parity, `HandoffContext` field population (including a session-parameters snapshot), the node → flow → agent `no_match` fallback ordering (three separate scenarios), `event.attempts` incrementing across consecutive no-matches on the same node and resetting on `enterNode()`, no-handler-anywhere leaving the session alive and usable next turn, an internally-cascaded event (`node_enter`) matching nothing correctly staying silent rather than triggering `no_match`, and a matched-but-non-stopping route correctly suppressing `no_match` entirely. No engine bugs found this milestone - the `compileAllExpressions()` `EventHandlers` walk M3.1 already added covered `no_match`'s own CEL expressions for free. M3.4 (cross-flow transition edge cases: `preserveParameters` interactions, mid-transition barge-in) is done and committed too, scoped down by explicit user choice: mid-transition barge-in (`ControlFrame::INTERRUPT` cancelling an in-flight `callWebhook`/`llmGenerate`, spec §9.3) was investigated and deliberately deferred rather than built, after tracing a real architectural obstacle - `FrameProcessor`'s shared base class (used by every processor in this SDK, not just the orchestrator) dispatches exactly one frame at a time on one dedicated thread per processor (`processingLoop()`), so a queued `ControlFrame::INTERRUPT` genuinely cannot be dequeued and acted on while that same processor is already blocked inside a `processFrame()` call - confirmed by reading `FrameProcessor.cpp` directly, not inferred. The one place in this codebase that already does real interrupt cancellation, `LLMProcessor`, sidesteps this entirely by never blocking its own `processFrame()` - it dispatches to an async, callback-driven `LLMTransport` and cancels via a plain thread-safe `transport->cancel()` call from whichever thread detects the barge-in, bypassing the frame queue. Reaching that same shape for `callWebhook` would mean making M3.1's bounded `future.wait_for()` wait pollable via a new thread-safe interrupt entry point bypassing the frame queue; reaching it for `llmGenerate`/generative nodes would additionally require giving those action kinds their own thread-pool-and-bounded-wait treatment from scratch, since M2.4 left them fully synchronous with no timeout at all - roughly doubling the work. Presented as a scoping choice (full both-action-kinds build vs. `callWebhook`-only vs. skip-for-now); the user chose to skip it for now, so it remains unimplemented, tracked here rather than silently dropped, for whoever picks it up next. `preserveParameters` cross-flow interactions were verified instead (a temporary self-test, 22 assertions since deleted, modeled directly on spec §19.2's `appointments`->`triage` worked example): `applyTransition()`'s existing `preserve_parameters` handling was already correct going in - unset defaults to `true` per spec's proto3-default rule, and `SessionState::clearAllParameters()` already erases `ParameterMeta` (including `attempts`) alongside parameter values when `false`, so a same-named parameter reused by a destination flow/node doesn't inherit a stale reprompt count - confirmed via a test that fails validation twice on `appointments`' own `visit_reason` before transitioning `preserve_parameters=false` into `triage`'s differently-scoped, same-named `visit_reason` form parameter and checking its `attempts` reads back 0, not 2. `Transition::NODE` (intra-flow) was confirmed to clear identically to `Transition::FLOW`, and a chained cross-flow cascade (two `FLOW` transitions firing back to back via `node_enter` routes in one `processFrame()` call, first hop `preserve_parameters=true` then second hop `false`) confirmed clearing applies correctly mid-cascade, not just at the top-level per-turn boundary. One real, previously-undiscovered engine bug surfaced while writing that self-test and was fixed: a `condition_cel` route referencing a session parameter that isn't set yet threw an uncaught `std::runtime_error` all the way out of `evaluateRoutesOnce()`, crashing the whole turn (or even `start()` itself, since condition routes are evaluated unconditionally on every internally-cascaded `node_enter` pass too, not just the top-level per-turn entry) - reproducing this required nothing exotic, just spec's own canonical §14/§19.1 config shape verbatim (`urgent_to_triage: visit_reason == "urgent"`, colocated on the same node as `visit_reason`'s own required-and-unfilled form declaration), meaning the spec's most-referenced worked example would have crashed this engine at session start if run as-is. Fixed by giving `ExpressionEvaluator::lookupField()`'s existing "field not present" `std::runtime_error` a distinguishable subtype, `FieldNotPresentError` (`ExpressionEvaluator.h`, IS-A `std::runtime_error` so every existing `catch`/propagate-uncaught site keeps working unchanged), and having `evaluateRoutesOnce()`'s condition-route loop catch specifically that subtype and treat it as "this route doesn't match, try the next one" - the same outcome an explicit `has(...)` guard would produce, without softening any *other* `std::runtime_error` (an unknown namespace, a genuine type mismatch), which still propagates and crashes loudly, unchanged. `SetParameterAction.value_cel`/`CustomToolAction.args_cel` evaluation is deliberately untouched by this - those compute a value meant to be used, so a reference to a genuinely-absent variable there is a real author bug worth failing loudly on, unlike a route condition simply not being relevant yet. `ParameterValidator::isRequired()`'s own `condition_cel` evaluation (a `Parameter`'s own optional-requiredness check) has the identical latent shape and was deliberately *not* touched this milestone - flagged here, not fixed, to keep this milestone's diff to what was actually verified end-to-end. **Follow-up, closed**: `isRequired()` now catches `FieldNotPresentError` the same way and returns `false` (not required yet, matching "this condition simply isn't satisfied" rather than "crash") - reached through `findUnfilledFormParameter()`, so a form parameter whose `condition_cel` gates on a sibling form parameter not yet filled (the same shape as spec's own `urgent_to_triage` example, just on a `Parameter` instead of a `Route`) no longer crashes `checkFormParameterAsk()`/`handleUtterance()`. Every other `std::runtime_error` (malformed CEL, non-bool result) still propagates unchanged. Verified via a temporary self-test (6 assertions, since deleted): absent-field condition returns `false` without throwing, a set field still evaluates normally in both directions, a genuinely non-bool condition still throws, and `required() == false` still short-circuits before `condition_cel` is even touched. `cel-cpp` - discovered during M0 to have no CMake build at all (Bazel-only, no vcpkg/Conan package) - was dropped as a dependency entirely, not just deferred: [Draft v2.10](requestflow-spec.md#010-what-changed-in-draft-v210) replaced it with M1.4's hand-rolled expression evaluator, the same move already made for the phrase grammar in [Draft v2.9](requestflow-spec.md#09-what-changed-in-draft-v29). `cel-cpp` is no longer part of this plan in any form. The one thing that *is* already true and worth reusing rather than rediscovering: `VASDK/src/goal/` and `VASDK/include/VASDK/goal/` are the closest existing analog (slot validation, a conversation simulator, three-method persistence, an intent router) and [requestflow-spec.md §3](requestflow-spec.md#3-relationship-to-existing-vasdk-components) already specifies exactly what's ported wholesale versus built fresh - Milestone 0 leaned on that directly.

## 1. How to Read This

- Each milestone is scoped to be independently shippable and CI-testable - via `OrchestratorConversationSimulator` once it exists, via a throwaway unit test before it does - mirroring `goal/`'s existing test posture rather than introducing a new one.
- **Phase 1 milestones are strictly ordered** (each genuinely depends on the previous one existing). **Phase 4 milestones are explicitly *not* ordered relative to each other** - §4 below replaces §15's single "Phase 4" bullet with one row per feature and a rationale for *when* you'd reach for it, so the choice of what to build next is driven by which concrete vertical needs it, not by document order.
- Every milestone cites its `requestflow-spec.md`/`requestflow-backend-spec.md` section(s) - this document defines sequencing and done-criteria, never new mechanism. If a milestone's behavior isn't already specified in one of those two files, it isn't ready to schedule yet; go write that section first.

## 2. Milestone 0 - Module Scaffolding (prerequisite to everything)

Not a phase from §15 - nothing in Phase 1 can start without it, and it's small enough to be its own milestone rather than folded into M1.1.

- New `va::orchestrator` module: `VASDK/src/orchestrator/`, `VASDK/include/VASDK/orchestrator/`, one class per file, mirroring `VASDK/src/goal/`'s existing layout exactly (confirmed present: `GoalDefinitionLoader`, `GoalManager`, `GoalState`, `GoalSlot`, `ConditionEvaluator`, `IntentRouter`, `GoalConversationSimulator`, `GoalStatePersistence` - each a `.h`/`.cpp` pair).
- A new CMake option gating the whole module (e.g. `VASDK_BUILD_ORCHESTRATOR`, default `OFF` until Phase 1 is usable), following the exact pattern the top-level `CMakeLists.txt` already uses for `VASDK_BUILD_CALLCENTER`/`VASDK_ENABLE_HIGHWAY`.
- `FetchContent` for `protobuf`, gated behind that same option, per [requestflow-spec.md §0.1](requestflow-spec.md#01-what-changed-in-draft-v21)/[§3](requestflow-spec.md#3-relationship-to-existing-vasdk-components)'s "one-target-per-dependency convention as every existing provider." (`cel-cpp` was originally planned here too but never wired - see [§0](#0-current-state) and [Draft v2.10](requestflow-spec.md#010-what-changed-in-draft-v210): it has no CMake build, and was dropped as a dependency entirely rather than resolved.)
- **Done when**: an empty `va::orchestrator` target builds clean with the option `ON`, and the rest of VASDK - `goal/`, the call center showcase, everything else - builds clean and unaffected with the option `OFF` (the default). Zero impact on any existing target is the acceptance bar here, not orchestrator functionality.

## 3. Phase 1 Milestones - Deterministic Core (strictly ordered)

Mirrors [requestflow-spec.md §15](requestflow-spec.md#15-rollout-plan) Phase 1, broken into buildable/testable steps.

**M1.1 - Proto schema.** Author the `.proto` schema from [§4](requestflow-spec.md#4-domain-model) (`Agent`/`Flow`/`Node`/`Route`/`Trigger`/`Parameter`/`Executor`/`Action`/`Transition`/`SessionSnapshot` and friends), generate C++ types via `protoc`, wire codegen into CMake. *Done when*: the schema compiles and a throwaway test can construct and serialize/deserialize an `Agent` message.

**M1.2 - Config loader + offline validator.** `OrchestratorConfigLoader::fromTextprotoFile`/`fromBinaryFile`/`fromDirectory` (including the [§14.1](requestflow-spec.md#141-splitting-config-across-files) multi-file composition rule), and `validate()` covering referential integrity, reachability, handler coverage, and the [§9.5](requestflow-spec.md#95-expect-and-inline-slot-elicitation) dead-end-node check. *Done when*: the [§14](requestflow-spec.md#14-config-format-example-textproto) `appointments-agent` example loads and validates clean, and a small set of deliberately-broken fixtures (bad `target_id`, an unreachable node, a dead-end node with no transition/event/turn-spanning mechanism) each fail `validate()` with a distinct, attributable error.

**M1.3 - Phrase-grammar compiler.** A standalone parser + matcher for [§22.1](requestflow-spec.md#221-phrase-grammar)'s phrase grammar (Draft v2.9: `{{name:type}}` capture, `(a|b|c)` alternation, `*`/`.` wildcards, uniform postfix `?`, bare `{canonical}`, leading `!` negative examples). Compiles `TrainingSet.intents[].phrases` into a matcher at load time - malformed phrase syntax, an unresolvable `type`, or a capture name reused across alternation branches all fail at compile time, never at match time - and matches an utterance against it, returning candidate intents with `extracted_parameters` and a specificity-based confidence score. No engine, no `NLUProvider` interface, no CEL dependency: pure string-in/matches-out, independently testable, and unblocked by the M1.4 CEL question below. *Done when*: [§22.4](requestflow-spec.md#224-worked-example)'s rewritten worked examples (volume-control alternation, climate-control zone+delta) match their documented example utterances with the documented `extracted_parameters`, and each of the deliberately-malformed phrase cases above fails compilation with a distinct, attributable error.

**M1.4 - Expression evaluator.** A standalone hand-rolled parser/evaluator for [§8](requestflow-spec.md#8-condition--expression-language)'s closed expression grammar (Draft v2.10: arithmetic `+ - * /`, comparisons `== != > >= < <=`, boolean `&& || !`, `has()`, `.contains()`, dotted field references), compiled once at load time against session `parameters` plus the well-known counters (`turnCount`, `repromptCount`, `sessionElapsedMs`) and, since they're mechanically the same "look up a name in a namespaced map" operation, `nlu.*`/`context.*`/`shared.*`/`event.*` too. `entity.*` is a later milestone (§5 below, [§25](requestflow-spec.md#25-entity-backed-cel-constants)) - it resolves against the `EntityDictionary` at compile time as a constant, not a runtime namespace lookup, which is a genuinely separate integration. No longer blocked - `cel-cpp` is dropped entirely, not deferred (see [§0](#0-current-state)). *Done when*: every expression in [§8](requestflow-spec.md#8-condition--expression-language)'s worked examples evaluates correctly against a fixture session/activation, and a malformed expression fails at load time, not at evaluation.

**M1.5 - Parameter model.** Port `GoalSlot`'s validation/normalization semantics ([§7](requestflow-spec.md#7-parameter-model-and-collection-policy)) into `Parameter`: `STRING`/`PHONE`/`EMAIL`/`DATE`/`TIME`/`DATETIME`/`NUMBER`/`INTEGER`/`BOOLEAN`/`ENUM`/`OBJECT`/`COMPOSITE`, plus the `condition_cel`/`validator_ref` escape hatches. *Done when*: `goal/`'s existing slot-validation test cases produce identical pass/fail/normalized-value results run against the ported implementation - this is a port, so a behavioral diff is a bug, not a design choice.

**M1.6 - Engine + processor, event/condition routes only.** `OrchestratorEngine` and `OrchestratorFrameProcessor` implementing [§6](requestflow-spec.md#6-route-evaluation-semantics) steps 3-6 for `event` and `condition` routes only - no `intent` routes yet, since those need `NLUProvider` (Phase 2). Includes the live `SessionState` object ([§13](requestflow-spec.md#13-public-api-surface-proposed-c)). *Done when*: a config containing only `event`/`condition` routes runs end-to-end through a real `Pipeline` in a test - `node_enter` fires, transitions apply, executor actions (`say`/`setParameter`/`clearParameter`/`emitEvent`) run in order.

**M1.7 - Session persistence.** `SessionSnapshot` proto (already defined in M1.1) plus `FileSessionPersistence` - binary by default, `TextFormat` in a debug mode - per [§10](requestflow-spec.md#10-session-state-and-persistence). *Done when*: a session snapshotted mid-flow and restored has identical `parameters`/`active_node_id` - this is one of [§16](requestflow-spec.md#16-acceptance-criteria-v1)'s acceptance criteria directly, so it doubles as a v1 sign-off check.

**M1.8 - `OrchestratorConversationSimulator` + metrics.** Mirrors `GoalConversationSimulator`'s scripted-turn design; wires [§11](requestflow-spec.md#11-observability)'s per-turn metrics into `MetricsCollector`/`CallMetrics`. *Done when*: every [§16](requestflow-spec.md#16-acceptance-criteria-v1) acceptance criterion that doesn't require NLU or webhooks is green in CI through the simulator, with no live model, webhook, or audio hardware.

**Phase 1 exit criterion** (= [requestflow-spec.md §15](requestflow-spec.md#15-rollout-plan)'s Phase 1 boundary): a build with zero `LLMProcessor`/`ToolDispatchProcessor` loads a real multi-flow, multi-file config and runs `event`/`condition`-only routes end-to-end in CI.

## 4. Phase 2-3 Milestones - Understanding, Then External Actions

Also strictly ordered within each phase; Phase 3 depends on Phase 1's engine but not on Phase 2's NLU (a build can add webhooks to an event/condition-only agent).

**Phase 2 - Understanding**
- **M2.1** - `NLUProvider` interface + `TrainingPhraseNLUProvider`, wrapping M1.3's already-built phrase-grammar compiler behind the polymorphic interface ([§5](requestflow-spec.md#5-nluprovider-interface)/[§22](requestflow-spec.md#22-nlu-training-data)). Ship this before the LLM-backed provider - it's the "LLM-optional by construction" claim in [§2](requestflow-spec.md#2-design-principles), and proving it first means the LLM-backed provider (M2.2) is demonstrably swappable rather than load-bearing.
- **M2.2** - LLM-tool-backed `NLUProvider`, structured classification call against `LLMTransport`. *Done when*: swapping M2.1 for M2.2 behind the interface requires zero changes to `OrchestratorEngine`/`OrchestratorFrameProcessor` - another direct [§16](requestflow-spec.md#16-acceptance-criteria-v1) criterion.
- **M2.3** - `intent` routes wired into [§6](requestflow-spec.md#6-route-evaluation-semantics) step 2/3, using either provider.
- **M2.4** - `llmGenerate` executor action ([§9.3](requestflow-spec.md#93-llmgenerate-and-barge-in)) and generative nodes ([§9.4](requestflow-spec.md#94-generative-nodes)) - the scoped LLM-tool loop.
- **M2.5** - `expect` executor actions, typed and bare ([§9.5](requestflow-spec.md#95-expect-and-inline-slot-elicitation)) - depends on M2.1-M2.3's extraction path, which is why §15 places it in Phase 2 rather than Phase 1 alongside the rest of the `Action` oneof.

**Phase 3 - External actions and hardening**
- **M3.1** - `callWebhook` with the full [§9.2](requestflow-spec.md#92-callwebhook-execution-model) reliability model: timeout, one retry on transient failures, per-endpoint circuit breaker, idempotency key.
- **M3.2** - A reference backend conformance pass against [requestflow-backend-spec.md](requestflow-backend-spec.md): implement one language's stub (Spring Boot or FastAPI, per [§8](requestflow-backend-spec.md#8-language-implementation-guides)) and verify the engine's M3.1 output against it end-to-end, including the HMAC signing ([§6](requestflow-backend-spec.md#6-authentication)) and idempotent-replay ([§5](requestflow-backend-spec.md#5-idempotency)) behavior. This is also the natural point to build the fixture set proposed in [requestflow-backend-spec.md §10](requestflow-backend-spec.md#10-open-decisions) - see §6 below, it doesn't have to wait for M3.2, but M3.2 is where the fixtures get proven against a real engine rather than only a mock.
- **M3.3** - `handoff`/escalation event handlers end-to-end.
- **M3.4** - Cross-flow transition edge cases: `preserveParameters` interactions, mid-transition barge-in.

**Phase 2/3 exit criterion**: [§16](requestflow-spec.md#16-acceptance-criteria-v1)'s remaining acceptance criteria (generative node with bounded exit, webhook retry/circuit-breaker under simulated failure) are green in CI.

## 5. Phase 4 Milestones - Cross-Vertical Extensions (build on demand, not in document order)

[§15](requestflow-spec.md#15-rollout-plan)'s Phase 4 paragraph lists roughly fifteen features from Draft v2.2 through v2.8 as one undifferentiated block. They share nothing structurally that forces an order - each is additive and independently testable against the Phase 1-3 core. The table below is meant to be scheduled by vertical need, matching the philosophy [§0.2](requestflow-spec.md#02-what-changed-in-draft-v22) already states for how these were scoped in the first place: build a feature when a concrete deployment target needs it, not speculatively.

| Feature | Spec section | Reach for it when... |
| --- | --- | --- |
| `TriggerFrame` consumption, ambient entry, proactive speech | [§9.7](requestflow-spec.md#97-external-and-scheduled-triggers) | Any deployment needs a flow to start from something other than user speech (a scheduled reminder, a sensor, a companion-app button) - agriculture and homelab both need this early. |
| Multi-intent co-firing | [§6.1](requestflow-spec.md#61-multi-intent-co-firing) | A vertical's utterances commonly bundle two independently-actionable requests ("play jazz and turn up the AC") - automotive-shaped. |
| Interrupt intents / mid-task cancel | [§6.2](requestflow-spec.md#62-interrupt-intents-and-mid-task-cancel) | Any vertical with slot-filling or generative nodes long enough that a user plausibly wants to bail mid-way - build this alongside the first generative node (M2.4) or the first multi-parameter form, whichever ships first. |
| Permission gate (`required_role`, `speaker_id`) | [§9.8](requestflow-spec.md#98-permission-gate) | A route gates something consequential enough to need an actor check (chemical application, door unlock) - agriculture/homelab. |
| `context.*`/`shared.*` namespaces | [§8.1](requestflow-spec.md#81-external-context-and-shared-state-namespaces) | Routes need continuously-changing external facts (`context.*` - vehicle speed, time of day) or cross-engine shared facts (`shared.*` - whole-home state). These are two separate milestones even though one section covers both, since they have different write semantics and no dependency on each other. |
| `event.*` namespace on `EmitEventAction` | [§8.2](requestflow-spec.md#82-the-event-namespace) | Natural to build alongside `TriggerFrame` consumption (its payload rides this namespace) or whenever the first author wants to pass data through an emitted event rather than just a bare name. |
| Offline-resilient `callWebhook` (`PendingActionStore`) | [§9.9](requestflow-spec.md#99-offline-resilient-callwebhook-store-and-forward) | A deployment has real multi-hour connectivity gaps - agriculture, specifically; automotive/homelab likely never need this. |
| Audit sink | [§11.1](requestflow-spec.md#111-audit-sink-for-consequential-actions) | Alongside the permission gate, for the same consequential-action deployments. |
| Hot-reload (`reloadAgent`) | [§13.1](requestflow-spec.md#131-hot-reloading-a-running-agent) | A homelab-style author wants to iterate on a live config without dropping the session - low priority unless that workflow is a near-term target. |
| Typed `customTool` codegen (`ToolSchema`) | [§23](requestflow-spec.md#23-typed-customtool-argument-and-result-codegen) | Once a vertical accumulates enough hand-written `customTool` handlers that a field-name typo has actually caused a production bug - build reactively, not ahead of the pain. |
| Typed `context.*` codegen (`ContextSchema`) | [§24](requestflow-spec.md#24-typed-context-codegen) | Immediately after `context.*` itself (above) ships, if that vertical's context provider is non-trivial enough to want compile-time field checking. |
| Entity-backed CEL constants (`entity.*`) | [§25](requestflow-spec.md#25-entity-backed-cel-constants) | Once `entities.textproto` ([§22](requestflow-spec.md#22-nlu-training-data)) exists for a vertical and routes are already retyping the same canonical values as CEL string literals. |
| Intent capture defaults | [§26](requestflow-spec.md#26-default-values-for-intent-captures) | Once a vertical's routes are visibly repeating the `has(nlu.x) ? nlu.x : default` ternary §26's own rationale describes - a code-smell trigger, not a calendar one. |
| Per-action `ExecutionMode` (`FIRE_AND_FORGET`/`BEST_EFFORT`) | [§9.10](requestflow-spec.md#910-action-execution-modes) | A vertical has a genuine fire-and-forget or best-effort use case (an analytics beacon, a non-critical preference sync) - otherwise `BLOCKING` (already in M1.6/M3.1) covers everything. |
| YAML/DSL-to-textproto authoring convenience | [§18](requestflow-spec.md#18-open-decisions) (first bullet) | Once `Parameter.constraints`/`EntityDictionary` hand-authoring is a measured pain point across two or more verticals, not before - this is tooling investment, justified by evidence, not a checklist item. |

Full management-plane versioning/environments and full RBAC ([§17](requestflow-spec.md#17-explicitly-out-of-scope-for-v1)) stay out of this roadmap entirely - they aren't Phase 4 items, they're explicitly deferred past v1, and nothing above depends on them.

## 6. Integrator-Facing Track - Parallel, Not Gated on Engine Code

[requestflow-backend-spec.md](requestflow-backend-spec.md)'s wire contract is plain JSON over HTTP and doesn't depend on `va::orchestrator` existing at all ([§0](requestflow-backend-spec.md#0-purpose-and-relationship-to-requestflow) is explicit about this). Everything here can start on day one, in parallel with Milestone 0 above, by a different person or team:

- **The OpenAPI document** proposed in [requestflow-backend-spec.md §10](requestflow-backend-spec.md#10-open-decisions) - request/response body schema, status-code contract, HMAC `securityScheme`, generated per `contractVersion`.
- **The conformance fixture set + CLI/script** also proposed there - the four fixture cases (happy path, not-found, malformed `contractVersion`, replayed idempotency key) plus a runner that POSTs them against a target URL.
- **A reference backend implementation** in one language (Spring Boot or FastAPI are the two with full code samples already in [§8](requestflow-backend-spec.md#8-language-implementation-guides)) as a working, clonable example - this is what M3.2 above ends up validating against, so building it early de-risks M3.2 rather than blocking on it.
- **The dev-tooling items** added to [requestflow-spec.md §18](requestflow-spec.md#18-open-decisions) in this same review pass (standalone validate/simulate CLI, `ValidationReport` diagnostic quality, route-trace/session-inspection tooling) *do* depend on Phase 1 existing (M1.2's `validate()`, M1.8's simulator) - these are listed here only as a pointer, not as parallelizable work.

## 7. Suggested Sequencing

- **Single track**: Milestone 0 → Phase 1 (strict) → Phase 2 → Phase 3 → Phase 4 (picked by vertical need, per §5's table).
- **Two tracks**: Track A runs the engine sequence above; Track B starts §6's integrator-facing work immediately and feeds M3.2 when Track A reaches it. This is the natural split if there's ever more than one person on this - the two tracks don't contend for the same files until M3.2.
- Whichever concrete vertical (automotive HVAC, agriculture, homelab) is the actual first target should be picked *before* Phase 4 starts, not after - it's what makes §5's table's "reach for it when" column resolve to a concrete, ordered list instead of staying a menu.

## 8. Definition of Done

The project-wide bar stays [requestflow-spec.md §16](requestflow-spec.md#16-acceptance-criteria-v1) - every milestone above cites which piece of §16 it contributes to specifically so that "is v1 done" never depends on re-deriving it from scratch.
